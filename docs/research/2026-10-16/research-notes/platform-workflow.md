# Сквозной путь агента: платформа и эксплуатация inn-check-ru

Исследование от 16 октября 2026, исходники `main`, `3e06046`. Цель: открытый инструмент для агентов с предсказуемыми stdio-вызовами. Код, установленные плагины, реестры и расписания не менялись. Ниже существующее поведение отделено от предложений; оценки S/M/L означают примерно 1–2, 3–5, 6–10 рабочих дней с тестами, а не обещанные сроки.

У проекта уже есть почти все отдельные операции: CLI/MCP/skill, диагностика сети, обновление индексов, финансовый расчёт, ручные блоки, пакет доказательств, Markdown/DOCX, снимки и watchlist. Однако пользовательский маршрут склеивается командами и памятью агента. Наибольшую пользу дадут продолжение одной проверки между этапами и предсказуемая свежесть локальных данных. Новый веб-сервис, база клиентов или обязательный фоновый демон для этого не нужны.

Текущая цепочка: установка → раздельные doctor/probe → ручной выбор обновлений → fetch → разрешённый человеком браузерный шаг → отдельная вклейка блока → dossier → снимок/watchlist → лог расписания. MCP предоставляет 14 инструментов, но не весь этот маршрут. Расширение умеет быструю проверку, ручную запись и вложение в существующий пакет; оно не завершает досье само.

## 1. Продолжение одной проверки через run_id — первый продуктовый приоритет, M

**Что есть.** Расширение сохраняет блок отдельно (`scripts/native_host.py:264–274`); инструкция затем требует вызвать `manual_block --вклеить` (`extension/README.md:49–55`). В MCP `due_diligence_dossier` запускает новый fetch (`mcp/tools_impl.py:364–378`), как и отраслевые/НДС-инструменты через `_сбор_или_ошибка` (`:300–307`). Следовательно, цепочка нескольких инструментов расходует сеть повторно и не гарантирует использование уже подтверждённого ручного результата.

**Предложение.** Локальный каталог запуска с непрозрачным `run_id`, ИНН, профилем, временем, версией движка, исходным fetch и добавленными ручными блоками. Сначала достаточно файлов JSON с атомарной заменой и блокировкой; SQLite нужен только при доказанной конкуренции. Добавить операции продолжения/формирования досье по run_id, сохранив существующие одноразовые вызовы. Произвольные пути клиента не нужны: идентификатор разрешается внутри явно выбранного каталога. Сохранять факты, не окружение и секреты; срок хранения задавать отдельно от свежести данных. Финансы, вердикт и документ читают один материализованный результат. Польза: агент воспроизводит проверку после смены контекста, а человек не связывает вручную имена файлов.

**Приёмка.** Fetch → закрытие MCP → новый процесс → ручной блок того же ИНН → досье/снимок. Сетевой счётчик второго этапа равен нулю; чужой ИНН отклонён; исходный пакет не изменён; явно устаревший run требует обновления выбранных источников.

## 2. Bootstrap и обновление кэшей по сроку годности — первый эксплуатационный приоритет, M

**Что есть.** `refresh_indexes.py:46–61` знает 14 обновляторов и не скачивает ничего без пользовательского конфига (`:85–118`). Это полезное ограничение. Но генератор предлагает ежемесячное расписание для выбранных модулей (`:182–234`), тогда как санкционная сверка отклоняет кэш старше 7 дней (`scripts/sanctions_check.py:87,543–548`). Такой план оставляет санкционный контур устаревшим значительную часть месяца. Probe живёт 24 часа и привязан к сети (`scripts/check_access.py:22–38`); это другой срок и другая задача.

**Предложение.** Команды `cache status` и `cache plan` показывают отсутствующее, дату публикации и загрузки, возраст, срок годности, объём и необходимость РФ-сети. Минимальный план для выбранного профиля, затем отдельное выполнение явно выбранных обновлений. Начать с общей таблицы политик поверх текущих модулей, не переписывать загрузчики. Генерировать расписание по ближайшему истечению TTL с запасом; большие отраслевые дампы включать осознанно. Секреты прокси остаются в окружении или хранилище хоста.

**Приёмка.** Чистый HOME выдаёт выполнимый ограниченный план; просроченные санкции не выглядят проверенными; недельный план поддерживает их свежесть; оборванная загрузка сохраняет последнюю годную версию. Повторный status не обращается к реестрам.

## 3. Диагностика готовности именно сценария и установленного пакета, S/M

**Что есть.** Doctor проверяет импорт `mcp`, несколько файлов под `repo/scripts`, ключ Checko и запись в кэш (`mcp/doctor.py:25–49`). Он не проверяет совместимый FastMCP импорт и версию SDK; отсутствие необязательного ключа уже правильно не считается критичным. У wheel только две console entry points (`pyproject.toml:42–44`), остальные возможности доступны модулями; поиск `scripts/` не описывает установленную структуру.

**Предложение.** Один пакетный `doctor --json --profile`, с режимами «без сети» и явным probe. Ответ разделяет: установка исправна, автоматический контур доступен, кэш готов, требуется человек, дополнительные источники отключены. Разрешать ресурсы через существующий путь установленного движка/importlib.resources. Выдавать конкретные next actions и безопасные команды для текущей ОС. Проверять присутствие ключа и источник настройки, не возвращать значение. Это можно открыть одним диагностическим MCP-инструментом; CLI не должен требовать MCP-extra ради собственной диагностики.

**Приёмка.** Wheel вне checkout, чистый HOME, Python 3.10/3.12, без SDK/с разрешённым SDK/с несовместимым SDK: правильные отдельные состояния и exit codes. Отсутствие Checko не блокирует базовый сценарий; диагностика не печатает ключи.

## 4. Машинный контракт ручного шага без автоматизации капчи, M

**Что есть.** Правила требуют согласия на браузер, человеческого решения капчи и честной неполноты (`references/brauzer.md:14–27`). Контракт блока уже проверяет дату, URL и объект (`:44–85`); `manual_block.py:167–203` пересчитывает доступность и итог. Следовательно, нужен удобный переход, а не новый распознаватель реестра.

**Предложение.** В run возвращать `pending_actions`: источник, допустимый URL, поисковые параметры без лишних персональных данных, обязательные поля, причина остановки, run_id. Импорт результата использует текущий валидатор. В Chrome показывать подтверждение привязки к выбранной проверке; в MCP/skill выдавать тот же объект. Отказ, незавершённая пагинация и истёкшая дата сохраняются как отдельные исходы. Состояние бизнес-процесса «нужен человек» должно работать в обычном JSON, независимо от поддержки протокольных Tasks клиентом.

**Приёмка.** Агент доходит до капчи, возвращает инструкцию и продолжает после ручного результата без повторного fetch. Отказ пользователя, чужой ИНН и неполная выдача не дают зелёного заключения. Внешний контент не становится командой запуска.

## 5. Поле → конкретный ответ → версия доказательств, M

**Что есть.** Пакет сохраняет сырые ответы с URL, временем, SHA-256 и размером (`scripts/evidence_pack.py:166–201`); досье указывает хеш входного файла и даты (`scripts/dossier.py:416–426`). Ручная вклейка намеренно создаёт новый fetch и запрещает менять `fetch.json` пакета (`scripts/manual_block.py:206–242`). Однако у результата нет общего обязательного указателя от каждого значимого поля к конкретному сырому ответу.

**Предложение.** Добавить лёгкую карту evidence refs: путь поля, source_id, raw response id, локатор JSON/XML/строки, observed_at, дата публикации и версия парсера. Для ручного ввода — отдельный тип подтверждения и ссылка на блок/вложение. Не объявлять любой скриншот доказательством истинности; не смешивать сохранённый ответ и пользовательское наблюдение. Для обновлённого run хранить производную версию и ссылки на прежнее основание. Начать со статуса, недостоверности, санкций и ключевых строк баланса.

**Приёмка.** Для каждого красного сигнала агент получает машинно читаемое основание и открывает нужный локальный фрагмент; другой ответ с похожим значением не подставляется. Верификация старого пакета остаётся успешной после ручного дополнения нового результата.

## 6. Предсказуемые MCP-схемы и настоящие побочные эффекты, S/M

**Фундамент.** Уже подтверждённые ошибки batch argv и оставленных после timeout процессов входят в обязательные исправления до расширения интерфейса; повторно они здесь не исследовались. Основание: `work/audit-logs/security-repro.json`, `mcp/tools_impl.py:108–117,265–274`.

Все декораторы сейчас без ToolAnnotations (`mcp/server.py:94–297`), хотя fetch имеет save, dossier пишет evidence_dir, access-check обновляет кэш. Описание «все read-only» не различает отсутствие записи во внешние сервисы и изменения локального окружения. По [схеме MCP](https://modelcontextprotocol.io/specification/2025-11-25/schema#toolannotations) это подсказки, не разрешения. [Официальный разбор](https://blog.modelcontextprotocol.io/posts/2026-03-16-tool-annotations/) отдельно объясняет: annotations не предотвращают prompt injection и не заменяют ограничения исполнения. [FastMCP 1.30](https://raw.githubusercontent.com/modelcontextprotocol/python-sdk/v1.30.0/src/mcp/server/fastmcp/server.py) уже принимает annotations: SDK2 для этого не требуется.

**Предложение.** Отделить получение/расчёт от явных save/export/update; статически аннотировать каждый инструмент по реальному поведению, включая кэш. Зафиксировать типизированный результат: транспортная ошибка, недоступные данные, частичный сбор и найденный риск различаются. Сначала общий Python-слой и CLI/MCP; расширению достаточно необходимых операций run/manual, полная копия всех кнопок не нужна.

**Приёмка.** Snapshot `tools/list` проверяет схемы и annotations; отрицательные сценарии дают структурированный исход; вызов без разрешённой записи не создаёт файлов. Отмена останавливает потомков и оставляет проверяемый статус run.

## 7. Наблюдение и follow-up как результат для хоста, M

**Что есть.** Watchlist собирает полный режим, делает снимок и diff, отдельно показывает непроверенное (`scripts/watchlist.py:16–41,320–345`). Расписание лишь печатает cron/launchd, не устанавливает его (`:389–452`). MCP умеет diff, но управление watchlist не входит в EXPECTED_TOOLS (`mcp/tools_impl.py:52–67`). Windows покрыт тестом native host (`.github/workflows/ci.yml:261–271`), собственного планировщика watchlist для него нет.

**Предложение.** Экспортировать машиночитаемый план следующей проверки и компактный отчёт изменений. Хост сам планирует повтор; CLI дополнительно может печатать Windows Task Scheduler XML. Не добавлять собственную рассылку или daemon. Бюджет запуска должен учитывать уже существующие ограничения: fetch 120 секунд/4 потока, batch 3 ИНН, граф 25 запросов (`fetch_counterparty.py:101–107,3266–3268`; `batch_check.py:98`; `affiliates_graph.py:71–76`). Уведомления хост отправляет только по своей явной политике.

**Приёмка.** Два запуска по одному ИНН дают воспроизводимый diff; сбой источника приходит как «не проверено», не «без изменений». Без разрешения расписание не появляется. Процесс без активного чата сохраняет отчёт, который следующий агент может прочесть.

## 8. Проверять опубликованный пользовательский маршрут, а не только импорт, M

**Что есть.** CI уже проверяет wheel вне checkout, ресурсы, uvx-обёртку, MCPB и Docker (`.github/workflows/ci.yml:128–198`). Это сильная база. Но импорт/initialize не проверяет связку cache → manual → dossier → watchlist. Настройки каналов отличаются: plugin предлагает Checko/DaData (`.claude-plugin/plugin.json:35–47`), MCPB — Checko/proxy (`packaging/mcpb/manifest.template.json:25–44`).

**Предложение.** Одна таблица возможностей и настроек каналов, общий export безопасного диагностического отчёта, тест установленного артефакта на синтетическом полном маршруте. Локальный сценарий с фикстурами выполнять на Linux/macOS/Windows; живой canary хранить отдельно от функционального pass/fail. Уже есть еженедельный canary с не-РФ раннера (`.github/workflows/canary.yml:3–7,25–32`); нужен явный статус географии и непокрытых контуров, а не обещание полного покрытия. Проверку реального браузера/MCP-хоста отмечать отдельно от headless smoke.

**Приёмка.** Новый пользователь без checkout завершает тестовое досье и повторный diff через документированные команды. В архиве, логах, run и JSON нет контрольных секретов. Один и тот же артефакт соответствует версии, схеме инструментов и описанию доступных операций.

## Порядок и границы протокольного развития

Начать с фундаментальных исправлений из пункта 6; затем параллельно 1 и 2, связать их диагностикой 3, пройти 4–5, после этого 7 и сквозную проверку 8. Для первого полезного релиза достаточно одного полного сценария: ИНН → готовность → сохранённый сбор → ручное дополнение → документ → повторная проверка.

Проект намеренно закрепляет SDK `mcp>=1.30,<2` (`pyproject.toml:35–37`, `.mcp.json:10–17`). [Официальная документация v2](https://py.sdk.modelcontextprotocol.io/whats-new/) описывает уже другую стабильную линию с MCPServer и протоколом 2026-07-28. Это отдельная миграция совместимости. [Cancellation старого протокола](https://modelcontextprotocol.io/specification/2025-11-25/basic/utilities/cancellation) предусматривает прекращение обработки и освобождение ресурсов; соответствие этому поведению требуется проверить в реальном stdio-клиенте. [Новая Tasks extension](https://tasks.extensions.modelcontextprotocol.io/specification/draft/tasks) помечена Draft и вводит working/input_required/terminal states и отдельную отмену. Её можно исследовать после устойчивого run-контракта, только с согласованными возможностями клиента; обязательный upgrade SDK и Tasks сейчас не обоснован.

Лимиты исследования: исходники и официальные спецификации просмотрены; новая установка у конечного пользователя, реальное взаимодействие браузер → MCP, планировщики ОС и актуальное покрытие реестров этим исследованием не подтверждались. Никаких внешних публикаций, установок или расписаний не выполнено.
