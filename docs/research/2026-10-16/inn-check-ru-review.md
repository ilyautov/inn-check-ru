# Аудит inn-check-ru

Проверено 16 октября 2026 года. Репозиторий: [ilyautov/inn-check-ru](https://github.com/ilyautov/inn-check-ru), `main` на коммите `3e06046995860b5360df5dd3a6110bd7108d36a3`, версия в манифестах `1.12.3`. Последний опубликованный релиз — [v1.12.3 от 30 сентября](https://github.com/ilyautov/inn-check-ru/releases/tag/v1.12.3); текущий main содержит последующие изменения. Исходники не изменялись.

Проект уже полезен как инструмент сбора досье для агента: есть самостоятельный движок, CLI, MCP, скилл, браузерное расширение, снимки и пакеты доказательств. Основной риск — достоверность светофора. Воспроизведены случаи, когда неизвестный признак становится отсутствующим, а рекомендация утверждает больше, чем подтверждают данные. Рекомендую исправить это и валидацию пакетного MCP-инструмента перед дальнейшим расширением функциональности.

## Что проверено

- Все **43 совместимых с macOS скрипта `eval/run_*.py` прошли** на Python 3.12.1. Единственный Windows-скрипт пропущен. Важно: это 43 файла проверки, а не 43 отдельных тестовых случая.
- `ruff check scripts/ eval/ mcp/ calibration/ packaging/ benchmark/` прошёл.
- MCP smoke прошёл полностью: логика инструментов, SDK-транспорт, живой stdio-хендшейк отдельного процесса.
- В проверенных зависимостях сайта и разрешённых MCP requirements сканеры не нашли известных уязвимостей. Это ограниченный результат сканирования зависимостей, а не гарантия безопасности проекта.
- Выполнен один живой CLI-запуск по ИНН `7707083893`, режим `всё`, без ключей и прокси, с изолированным пустым кэшем. Завершился с кодом 0 за **29,41 с**: **4 `ok`, 7 `пусто`, 22 `не проверено`** из 33 блоков. Причины включают отсутствие локальных индексов, ручные браузерные источники, сеть/TLS; НПД неприменим к юрлицу. Это наблюдение работы сборщика; истинность данных реестров независимо не сверялась.
- Прочитаны актуальные логи GitHub: [CI](https://github.com/ilyautov/inn-check-ru/actions/runs/38256727706) и [canary](https://github.com/ilyautov/inn-check-ru/actions/runs/38271936591), оба от 12 октября, завершились ошибкой. Причины разобраны ниже.

Полная сводка запусков: [verification.json](verification/verification.json). Успешные штатные проверки не покрывают найденные ниже пограничные сценарии.

### H1. Параметры CLI проходят через список ИНН

Место: [mcp/tools_impl.py:265](https://github.com/ilyautov/inn-check-ru/blob/3e06046995860b5360df5dd3a6110bd7108d36a3/mcp/tools_impl.py#L265).

`counterparty_batch` считает число элементов и преобразует их в строки, затем передаёт как аргументы `batch_check.py`. CLI допускает флаги и файлы, поэтому контракт инструмента «список ИНН» не сохраняется.

В безопасном опыте без сети `counterparty_batch(["--resume", "<temp>/unexpected.csv", "bogus"])` вернул `статус: ок` и создал CSV. Аналогичный вызов дописал CSV-данные в существующий тестовый `config.txt`. Один элемент с путём CSV раскрылся в **51 результат**, обходя лимит 50 ИНН.

Это дополнительная возможность чтения/записи файлов через ввод, заявленный списком ИНН; она не относится к штатному сохранению снимков. Выполнение shell-команд, RCE или удалённая неавторизованная атака не установлены.

Исправление: проверить тип и контрольное число каждого ИНН до формирования команды; пути и опции отвергать. Передавать проверенный список через stdin или вызывать движок через API. Добавить проверки отсутствия неожиданных файловых операций и обхода лимита. [Свидетельства](verification/security-repro.json).

### H2. Неизвестные финансовые данные становятся отсутствующим риском

Места: [fin_scoring.py:160](https://github.com/ilyautov/inn-check-ru/blob/3e06046995860b5360df5dd3a6110bd7108d36a3/scripts/fin_scoring.py#L160), [fin_scoring.py:222](https://github.com/ilyautov/inn-check-ru/blob/3e06046995860b5360df5dd3a6110bd7108d36a3/scripts/fin_scoring.py#L222), [profiles.py:577](https://github.com/ilyautov/inn-check-ru/blob/3e06046995860b5360df5dd3a6110bd7108d36a3/scripts/profiles.py#L577).

В синтетическом чистом входе рост выручки с `100000` до `500001` при неизвестной численности даёт пустые списки `флаги` и `не_проверено`. Транзитный профиль объявляется отсутствующим, результат `клиент_115фз` — 🟢.

Сильнее: численность **0 уже есть** в `дампы_фнс.численность_сотрудников`, куда её кладёт сборщик, но скорер читает другие блоки. Перенос ровно того же нуля в `риски.численность_сотрудников` меняет 🟢 на 🔴. Это рассогласование схемы, а не спор о выбранном пороге.

Аналогично отсутствие уставного капитала превращается в «ЧА ниже УК: отсутствует». При отрицательных текущих ЧА и неизвестных ЧА прошлого года двухлетний стоп-сигнал тоже объявляется отсутствующим. Текущее поле `не_проверено` эти пробелы не отражает.

Исправление: возвращать для каждого правила структурированный статус `найден / отсутствует / не проверен` и перечень необходимых данных; согласовать источники численности, сохранять ноль, год и происхождение. Не выводить отсутствие сигнала из отсутствия флага. [Семь воспроизводимых сценариев](verification/scoring-repro.md).

### H3. Зелёный вердикт противоречит непроверенному риску

Место: [profiles.py:713](https://github.com/ilyautov/inn-check-ru/blob/3e06046995860b5360df5dd3a6110bd7108d36a3/scripts/profiles.py#L713).

Удаление `риски.массовый_руководитель` из чистой фикстуры даёт одновременно:

```text
массовый_руководитель: не проверен
светофор: 🟢
рекомендация: руководитель ... не массовый
```

В профиле `клиент_115фз` этот риск поднимает тревожность до 🔴. Защита от зелёного из-за неполного ручного блока есть, но для автоматического блока такой же пробел проходит. Парсер рисков может штатно вернуть источник `ok` с непроверенными деталями. Досье переносит итоговую рекомендацию в документ.

Исправление: учитывать неизвестные обязательные риски независимо от способа сбора, включая риски с повышением уровня до 🔴. Формировать фразы рекомендации из подтверждённых фактов; проверка источника в целом не подтверждает каждое его поле. [Воспроизведение](verification/scoring-repro.md).

### H4. Отчётность за 2025 и 2023 годы считается двумя годами подряд

Место: [fin_scoring.py:191](https://github.com/ilyautov/inn-check-ru/blob/3e06046995860b5360df5dd3a6110bd7108d36a3/scripts/fin_scoring.py#L191).

После сортировки скорер берёт две первые записи без проверки разницы годов. При отрицательных ЧА и убытке за **2025 и 2023**, без отчётности за 2024, он выдаёт `ча_отрицательные_2года` и `убыток_2года` с порогом «два года подряд», `год: 2023–2025`, пустой список непроверенного и красный стоп в профиле отсрочки. Многолетняя динамика выручки также может называться годовой.

Исправление: для правил «год к году» и «подряд» сравнивать Y с Y−1; сначала устранять дубли и выбирать редакцию отчётности. Пропуск года должен давать неизвестный результат соответствующего правила. [Воспроизведение](verification/scoring-repro.md).

### H5. Ручная установка по README неполна

Место: [README.md:136](https://github.com/ilyautov/inn-check-ru/blob/3e06046995860b5360df5dd3a6110bd7108d36a3/README.md#L136).

Предлагается скопировать `SKILL.md`, `references/` и `scripts/`, но пропущен `data/`. Точное повторение этой инструкции во временной папке приводит к exit 1 у `python scripts/profiles.py --list`: не читается `data/profiles_ru.json`. Теряются также канон порогов, отраслевые нормы и сертификат. ZIP и wheel данные включают; замечание относится к документированному ручному способу.

Исправление: добавить `data/` и проверять документированный состав установки из отдельной папки, вне checkout. [Свидетельства](verification/quality-repro.md).

### M1. Таймаут не останавливает потомков

Место: [mcp/tools_impl.py:108](https://github.com/ilyautov/inn-check-ru/blob/3e06046995860b5360df5dd3a6110bd7108d36a3/mcp/tools_impl.py#L108).

`subprocess.run` по таймауту завершает `batch_check`, но не запущенный им fetch. В опыте с безопасной заглушкой ответ «не проверено» пришёл через 0,15 с; потомок через 0,8 с дописал маркер. Реальные последствия — продолжающиеся запросы и расход ресурсов после завершения MCP-вызова. Бесконечная работа или неограниченное размножение процессов не доказаны.

Исправление: изолировать запуск в группу процессов, по таймауту завершать и собирать всю группу; реализовать эквивалент для Windows. [Свидетельства](verification/security-repro.json).

### M2. Нестабильная проверка параллелизма

Место: [run_fetch_eval.py:549](https://github.com/ilyautov/inn-check-ru/blob/3e06046995860b5360df5dd3a6110bd7108d36a3/eval/run_fetch_eval.py#L549).

Последний GitHub CI упал на диагностике «opener шарятся между потоками». Тест хранит числовые `id(opener)` за несколько волн с разными executor. После освобождения объекта Python может повторно использовать его адрес; тест принимает новый объект за прежний.

С фабрикой, создающей отдельный объект на каждый вызов, получено **9 ложных падений из 20**. Если удерживать те же объекты до конца теста — **0 из 20**. Реальные urllib opener локально прошли 50 повторов; точное событие аллокатора из GitHub с ними не воспроизведено. Поэтому подтверждён дефект проверки; совместный CookieJar в рабочем коде не установлен.

Исправление: удерживать реальные ссылки, проверять принадлежность живых объектов потокам; параллелизм подтверждать барьером или счётчиком одновременных вызовов. [Свидетельства](verification/quality-repro.md).

### M3. Canary на чистом runner падает из-за пустого кэша

Места: [check_access.py:473](https://github.com/ilyautov/inn-check-ru/blob/3e06046995860b5360df5dd3a6110bd7108d36a3/scripts/check_access.py#L473), [canary.yml:19](https://github.com/ilyautov/inn-check-ru/blob/3e06046995860b5360df5dd3a6110bd7108d36a3/.github/workflows/canary.yml#L19).

Канарейка получает корректный ответ `(None, «не проверено: индекса нет»)` и объявляет его поломкой парсера `fetcher вернул не dict (NoneType)`, игнорируя состояние доступности. Workflow индексы не готовит. На изолированном пустом кэше это воспроизведено для реестров ЦБ без сетевых запросов. В актуальном GitHub-логе аналогичные ошибки есть у 12 блоков.

Помимо этого, в прогоне были сетевые/TLS-ошибки и исчерпан общий бюджет 300 с. Красный canary поэтому не доказывает, что схемы всех этих реестров изменились.

Исправление: отдельно учитывать неподготовленный индекс и недоступный источник; проверять парсеры на подготовленных входах. Сетевой canary должен сообщать покрытие и причины пропусков; ошибкой контракта считать проверенное нарушение схемы. [Свидетельства](verification/quality-repro.md).

## Что сделано хорошо

- Основной движок использует стандартную библиотеку Python; MCP SDK подключается отдельно. Одна реализация обслуживает несколько интерфейсов.
- Источники различают данные, подтверждённое отсутствие записей и невозможность проверки. Оговорки о неполном покрытии попадают в досье. Проблема возникает на части переходов от этих данных к сигналам и рекомендации.
- Проверки содержательные: записанные ответы источников, дрейф схем, запрет сетевых вызовов в offline, снимки, целостность пакетов и проверка wheel вне checkout.
- Native host проверяет команды и входные данные; расширение использует минимальные разрешения и текстовый вывод. TLS-верификация включена; subprocess не запускается через shell.
- Есть единые данные порогов, контроль версий артефактов, ограничения и описанная модель угроз. Отдельного убедительного дефекта производительности в рамках аудита не установлено.

## Что осталось за границей проверки

Реальная установка расширения/native host в браузер, локальное поведение Windows, сессия инструмента внутри полноценного агента, независимая сверка ответов реестров, весь Git history на секреты и визуальный аудит всех страниц сайта. Сценарии с предварительной загрузкой больших индексов не прогонялись. Один живой CLI-запуск и stdio-хендшейк не заменяют эти проверки.

## Порядок исправлений

1. Закрыть параметры CLI в MCP и добавить регрессионные проверки файловых побочных эффектов.
2. Исправить контракт данных скоринга, неизвестные сигналы и формирование рекомендации; закрепить семь приведённых сценариев тестами.
3. Исправить сравнение годов и ручную установку.
4. Починить flaky-проверку и разделить диагностику сети, кэша и схем в canary; затем проверить результат в GitHub CI.
5. Провести один полный сценарий из чистой установки в агенте с заранее согласованным покрытием источников и ручными шагами.

Итог аудита: **требуются исправления — 5 замечаний высокого и 3 среднего уровня; критических не установлено**. Новые источники сейчас менее полезны, чем устранение ложных утверждений в итоговом вердикте.
