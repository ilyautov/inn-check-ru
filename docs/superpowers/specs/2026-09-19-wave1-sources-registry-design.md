# Волна 1: реестр источников, три состояния, канарейки, probe, профили цели

**Дата:** 19.09.2026 · **Версия на входе:** 1.6.1 · **Версия на выходе:** 1.7.0
**Статус:** контракт для параллельной реализации (5 независимых потоков).

## 0. Что показал живой прогон (основание)

Сеть исполнения — не-РФ (Стокгольм). Сырой ответ `pb.nalog.ru` (`search-proc.json`,
`mode=search-ul-result`) содержит поля `inn, ogrn, namec, namep, sulst_ex, sulst_name_ex,
pr_liq, invalid, okved2main, okved2mainname, dtreg, dtogrn, regionname, okopf12, predo, token`.
Угаданных в коде `taxDebt/debt, disqualified, massAddress/addressMass, massHead/headMass,
employeeCount/ssch, taxMode/specialRegime, sschYear` в ответе нет → 7 из 8 риск-флагов всегда
`null` при `_доступность.риски = "ok"`. Совпадает только `invalid`. Детальные флаги (долг,
массовость, ССЧ, спецрежим) лежат за `token` в `company-proc.json` (`get-request` → id,
`get-response` → 500 с не-РФ IP).

Сырой ответ `egrul.nalog.ru` (`search-result/<t>`, `rows[0]`) содержит
`c, g, cnt, i, k, n, o, p, r, t, pg, tot, rn`. Полей `a` (адрес), `e`, `tp` нет → адрес всегда
`null`; `k` = вид субъекта (`ul`/`fl`), не статус.

ГИР БО: `advanced-search/organizations/search?query=<ИНН>&page=0` → `content[]` с `id, inn,
ogrn, shortName, region, okved2`; `nbo/organizations/<id>/bfo/` → список `{id, period,
gainSum, actives, actualBfoDate}`. Канарейка с реальными строками: ИНН 5036045205 (три года
выручки/1300 отличаются). ИНН 2309085638 показывает одинаковый `gainSum` за 2025 и 2024 —
семантику `gainSum` проверить по детальной форме, не доверять как «выручке» без сверки с 2110.

МСП: `rmsp.nalog.ru/search-proc.json?query=<ИНН>` → `data[]`, формат подтверждён
(фикстура `eval/fixtures/registries/msp_504110181262.json`).

Итог: тихая деградация — не гипотеза, а текущее состояние. Поэтому порядок: сначала контракт
полей по фактическим ответам, потом реестр, потом всё остальное.

## 1. Модель трёх состояний

### 1.1 Уровень блока — `_доступность[<id источника>]`

Было: строка. Стало: словарь фиксированной формы.

```json
{
  "состояние": "ok" | "пусто" | "не проверено",
  "причина": "строка или null",
  "канарейка": "ok" | "провал" | "не запускалась",
  "tier": "🟢" | "🟡" | "🔴" | "⚪",
  "требует": "сеть" | "кэш" | "браузер" | "ключ",
  "дата": "YYYY-MM-DD"
}
```

- `ok` — источник ответил, **все поля контракта найдены** в сыром ответе, запись по ИНН есть.
- `пусто` — источник ответил, контракт совпал, записи по этому ИНН нет. Это подтверждённое
  отсутствие: «не в реестре МСП», «нет отчётности в ГИР БО», «нет в РНП». Оно **является
  фактом** и участвует в вердикте.
- `не проверено` — всё остальное: сеть, TLS, гео, капча, дедлайн, схема изменилась,
  скриптом не покрыто, пропущено по профилю. В `причина` — машинно-различимый префикс:
  `сеть:`, `tls:`, `гео:`, `капча:`, `дедлайн:`, `схема:`, `не покрыто:`, `профиль:`, `probe:`.

Правило «схема изменилась»: если ответ пришёл и распарсился как JSON, но хотя бы одно поле
из `контракт` дескриптора отсутствует в сырой записи → состояние `не проверено`,
причина `схема: не найдено поле <имя>`. Никогда не `ok` с пустыми целевыми полями.

### 1.2 Уровень поля

Внутри блока со состоянием `ok` отсутствие признака кодируется **явным значением**
(`false`, `0`, `"нет"`, `[]`), а `null` допустим только для полей, которых нет в контракте
источника (например, `адрес` из ЕГРЮЛ — источник его не отдаёт; такое поле сопровождается
`"адрес_источник": "не отдаётся egrul search; см. pb/выписка"`). Внутри блока со состоянием
`пусто` или `не проверено` блок данных — `null`, и потребитель обязан смотреть в
`_доступность`, а не в поле.

### 1.3 Уровень вердикта — `_итог_проверки`

Новый верхнеуровневый блок в выводе `fetch_counterparty.py`:

```json
{
  "источников": 12, "ok": 5, "пусто": 2, "не_проверено": 5,
  "deal_killer_источники": ["егрюл", "риски", "спецреестры", "фссп", "суды", "банкротство", "санкции"],
  "deal_killer_не_проверено": ["спецреестры", "фссп", "суды", "банкротство"],
  "проверка_состоялась": false,
  "вывод": "проверка НЕ состоялась: 4 из 7 deal-killer-источников не проверено — светофор 🟢 недопустим"
}
```

Правило: `проверка_состоялась = (не проверено среди deal-killer) * 2 <= (всего deal-killer)`.
`санкции` в этом списке отражают `sanctions_check.py`, который fetch не запускает; его
состояние берётся из кэша перечней (есть свежий кэш → «кэш», нет → «не проверено»).

## 2. Реестр источников — `scripts/sources.py`

Один дескриптор на источник, plain dict без callable (чтобы `check_access.py` импортировал
реестр без сетевого модуля). Форма:

```python
"егрюл": {
    "название": "ЕГРЮЛ/ЕГРИП — карточка (egrul.nalog.ru)",
    "tier": "🟢",
    "требует": "сеть",              # сеть | кэш | браузер | ключ
    "deal_killer": True,            # участвует в _итог_проверки
    "профили": "*",                 # "*" или список id профилей из data/profiles_ru.json
    "probe": {"url": "https://egrul.nalog.ru/", "method": "GET",
              "ok_http": [200, 307], "ожидаем": "html"},   # лёгкий запрос для check_access
    "контракт": ["n", "o", "i", "g", "r", "k"],           # поля сырой записи, без которых не ok
    "канарейка": {"инн": "7707083893",
                  "ожидаем_непустые": ["наименование_полное", "огрн", "руководитель"]},
    "при_отказе": "не проверено",   # не проверено | пропустить
    "документация": "https://egrul.nalog.ru/",
}
```

Сетевые функции регистрируются в `fetch_counterparty.py`:

```python
FETCHERS = {"егрюл": fetch_egrul, "риски": fetch_risks, ...}   # id -> callable(opener, inn) -> (data, av_dict)
def run_source(source_id, inn, opener=None, профиль=None) -> (data, av_dict)
```

`main()` собирает `_доступность` и `_итог_проверки` из реестра, а не руками. Порядок обхода —
порядок ключей в `SOURCES`. Источники с `требует: браузер` не имеют fetcher и всегда дают
`не проверено`, причина `не покрыто: <текст>`.

Добавить источник = одна запись в `SOURCES` + одна функция в `FETCHERS` + фикстура.

## 3. Контракт и фикстуры — `eval/fixtures/net/`

Для каждого сетевого источника: `<id>_<инн>.raw.json` (сырой ответ, токены заменены на
`"<token>"`) и `<id>_<инн>.expected.json` (ожидаемый распарсенный блок + ожидаемая
`_доступность`). `eval/run_fetch_eval.py` гоняет парсеры офлайн против фикстур и, отдельно,
**дрейф схемы**: из raw удаляется каждое поле контракта по очереди → парсер обязан вернуть
`не проверено` с `схема:`. Eval подключается в `ci.yml`.

## 4. Probe — `scripts/check_access.py`

Читает `SOURCES[*].probe`, бьёт параллельно (threads, stdlib) с таймаутом 10 с, классифицирует:

| состояние | признак |
|---|---|
| `доступен` | HTTP в `ok_http` |
| `tls` | `ssl.SSLCertVerificationError` → подсказка `scripts/install_ca.py` |
| `гео` | таймаут, 403, 451, 503 |
| `dns` | `socket.gaierror` |
| `капча` | 200 + маркер капчи в теле |
| `ошибка` | остальное |

Вывод: таблица в stderr, JSON в stdout, кэш `~/.cache/inn-check-ru/access.json`:

```json
{"дата": "2026-09-19T14:00:00", "ip_класс": "не-РФ|РФ|неизвестно",
 "источники": {"егрюл": {"состояние": "доступен", "http": 307, "мс": 350, "причина": null}}}
```

`fetch_counterparty.py` читает кэш (TTL 24 ч): источник в состоянии `гео|tls|dns` → блок сразу
`не проверено`, причина `probe: <состояние>`, сеть не дёргается, дедлайн не съедается.
`COUNTERPARTY_IGNORE_ACCESS_CACHE=1` отключает. Флаг `--канарейки` гоняет `FETCHERS` на
канареечных ИНН и сверяет `ожидаем_непустые`; используется еженедельным CI-джобом.

Прокси: `HTTPS_PROXY` уже уважается `urllib.request.build_opener` — только документация.

## 5. Корень УЦ Минцифры — `scripts/install_ca.py`

Скачивает корневой и промежуточный сертификаты Национального УЦ (публикуются на
gosuslugi.ru / digital.gov.ru), сверяет SHA-256-отпечаток с **опубликованным** значением,
зашитым в скрипт со ссылкой на источник, конвертирует DER→PEM (stdlib), пишет
`~/.cache/inn-check-ru/ca/russian_trusted_bundle.pem`. `_build_ssl_context()` в
`fetch_counterparty.py` подхватывает этот файл автоматически, если он существует
(`COUNTERPARTY_CA_BUNDLE` по-прежнему имеет приоритет). Верификация не отключается никогда.
`--проверить` делает три запроса (fedsfm, rosstat/opendata, npchk) с новым контекстом и
печатает результат.

## 6. Профили цели — `data/profiles_ru.json` + `scripts/profiles.py`

Идентификаторы профилей (фиксированы, на них ссылается `SOURCES[*].профили`):

| id | вопрос пользователя | по умолчанию |
|---|---|---|
| `нейтрально` | «кто это?» — карточка без вердикта и рекомендации | **да** |
| `отсрочка` | «отгрузить в долг?» — ЧА, ФССП, чем взыскивать | |
| `предоплата` | «внести предоплату?» — способность исполнить: ресурсы, лицензии | |
| `подрядчик` | «нанять подрядчиком?» — РНП, СРО, трудовые споры | |
| `доля` | «купить бизнес / войти в долю?» — залоги, история учредителей | |
| `клиент_115фз` | «принять как клиента?» — РФМ, ЗСК, бенефициары | |
| `самопроверка` | «как меня видят?» — те же данные, зеркально | |

Профиль описывает: `описание`, `вопрос`, `источники_обязательные`, `deal_killers` (id
сигналов), `severity_override` ({id сигнала: 🔴/🟡/⚪}), `рекомендации` (три фразы для
🟢/🟡/🔴 либо `null` для нейтрального), `формулировка` (`факты` | `вердикт`).

Каталог id сигналов — единый: имена риск-флагов из `риски`/`спецреестры` + id флагов
`fin_scoring` + `ликвидация`, `не_в_мсп`, `рфм_совпадение`, `рнп`, `фссп_крупные`,
`суды_ответчик_крупные`, `банкротство`. `scripts/profiles.py`: `load()`, `sources_for(id)`,
`resolve(fetch_json, fin_json, profile_id) -> {"светофор", "поднят_сигналами", "рекомендация",
"не_проверено_deal_killer", "проверка_состоялась"}`. Для `нейтрально` `светофор = null`,
выдаётся список фактов. Если `_итог_проверки.проверка_состоялась == false` — светофор `null`
и `рекомендация = "проверка не состоялась"` в любом профиле.

`fetch_counterparty.py --профиль <id>` собирает только `SOURCES`, где `профили == "*"` или
содержит id; остальные — `не проверено`, причина `профиль: не требуется для <id>`.

SKILL.md: шаг 1 получает вопрос о цели (список выше, по умолчанию `нейтрально`); шаг 5
ссылается на `profiles.py`, рекомендация «отсрочка / предоплата / избегать» перестаёт быть
единственной.
