## 1. Задача 19 — ленивый сбор и ранний выход (поток F)

**Проблема.** `collect()` идёт по источникам последовательно под общим дедлайном 120 с:
медленный ЕГРЮЛ съедает бюджет следующих блоков. SKILL.md декларирует «найден deal-killer →
дальше можно не собирать, ~70% отсева здесь», код так не делает — собирает всё всегда.

**Решение — три слоя, в порядке важности.**

### 1.1 Фазы сбора в дескрипторе

В `SOURCES[*]` добавляется `фаза`: `"quick"` | `"досье"`. Quick-фаза — источники, способные
дать deal-killer дёшево: `егрюл`, `риски`, `спецреестры`, `санкции` (кэш, мгновенно).
Досье-фаза — `финансы`, `мсп`, `нпд`, `еркнм`, `рнп`. Браузерные (`фссп`, `суды`,
`банкротство`) остаются «не покрыто» в обеих.

### 1.2 Ранний выход

`collect(inn, профиль=None, режим="полный")`, где `режим`:
- `quick` — только quick-фаза, затем стоп;
- `полный` (по умолчанию) — quick-фаза, затем проверка на deal-killer, затем досье-фаза;
- `всё` — без раннего выхода (для снимков мониторинга: дифф должен видеть все поля).

После quick-фазы вызывается `profiles.resolve()` на собранном. Если светофор `🔴` и
`режим == "полный"` — досье-фаза не собирается, каждый её источник получает
`не проверено` с причиной `ранний выход: deal-killer найден на quick-фазе`.
В выводе — блок `_сбор`: `{"режим", "фаза_остановки", "секунд", "источников_собрано",
"ранний_выход": bool, "причина_остановки"}`.

Резолвер профиля `нейтрально` светофор не выдаёт, поэтому ранний выход в нём не срабатывает
никогда — это правильно: нейтральный режим показывает факты, а не отсеивает.

### 1.3 Параллельный сбор внутри фазы

Источники одной фазы собираются `ThreadPoolExecutor` (макс. 4 потока, stdlib): они
независимы, общий `opener` не шарится — каждый поток делает свой через `_make_opener()`
(cookiejar не потокобезопасен). Дедлайн остаётся общим. Ожидаемый эффект: quick-фаза
укладывается в секунды вместо десятков секунд.

`COUNTERPARTY_SEQUENTIAL=1` возвращает последовательный обход (отладка, воспроизводимость).

### 1.4 Спецреестры service.nalog.ru — живая разведка

`proc.json` на `dismissal/zd/invalid` отдаёт HTML 200 вместо JSON: предполагавшаяся схема
неверна. Разведать живыми запросами реальную форму (пути сервисов ФНС менялись:
`service.nalog.ru/disqualified.do`, `/zd.do`, `/invalid-addresses.do` и их `*-proc.json`),
найти рабочую — либо зафиксировать в дескрипторе `не покрыто` с точной причиной и снять
ложное обещание из таблицы источников. Ничего не выдумывать: работает — контракт и
фикстура; не работает — честная причина.

## 2. Задача 8 — батч + MCP-поверхность (поток G)

### 2.1 `scripts/batch_check.py`

Вход: CSV/TSV (автоопределение разделителя), колонка с ИНН определяется по заголовку
(`инн`, `inn`, `ИНН контрагента`…) или `--колонка N`; либо список ИНН в аргументах; либо
`--stdin` (по ИНН на строку). Дубли схлопываются, невалидные ИНН не отбрасываются молча —
попадают в вывод со статусом `некорректный ИНН`.

Обработка: по каждому ИНН `collect(режим="quick", профиль=…)` → `profiles.resolve()`.
Параллельно (макс. 3 ИНН одновременно — уважение к ФНС), с прогрессом в stderr.
`--дальше` догружает досье по тем, кто не 🔴.

Выход: `--csv` (таблица: ИНН, название, светофор, сигналы, проверка_состоялась, что не
проверено), `--json` (полный), по умолчанию — markdown-таблица в stdout. Сортировка: 🔴,
затем `null` (проверка не состоялась), затем 🟡, 🟢 — опасное и непроверенное наверху.

Устойчивость: сбой по одному ИНН не роняет батч — строка со статусом `не проверено` и
причиной. `--продолжить <файл>` дописывает результаты в существующий CSV, пропуская уже
проверенные ИНН (батч на сотню контрагентов переживает обрыв).

### 2.2 MCP-поверхность

В `mcp/tools_impl.py` + `mcp/server.py` добавляются инструменты:
- `counterparty_verdict(inn, profile="нейтрально")` — fetch + fin + resolve одной командой,
  возвращает светофор, сигналы, рекомендацию, что не проверено. Это главный инструмент,
  которого не хватало: раньше модель получала сырой JSON и сводила вердикт сама.
- `counterparty_batch(inns, profile)` — батч по списку (лимит 50 за вызов).
- `access_check()` — таблица доступности источников с текущей сети.

`EXPECTED_TOOLS` и дымовой тест обновляются. Ни один инструмент не падает traceback'ом.

## 3. Задача 9 + §12 — отпечатки и мониторинг (поток H)

### 3.1 `scripts/snapshot.py` — отпечаток вместо полного слепка

**Противоречие роадмапа:** снимок нужен целиком для диффа и ретроспективы, и не нужен
целиком — это чужие персданные, вес и время. **Разрешение:** хранить нормализованный
отпечаток.

```json
{
  "версия_формата": 1, "инн": "…", "дата": "2026-09-19T20:00:00",
  "поля": {"статус": "…", "руководитель": "…", "адрес": null, "недостоверность_сведений": false,
           "ликвидация": false, "налоговая_задолженность": null, "дата_прекращения": null,
           "год_отчётности": 2025, "чистые_активы": 79368565.0, "выручка": 396350822,
           "мсп_категория": null, "мсп_статус": "не в реестре"},
  "состояния": {"егрюл": "ok", "риски": "ok", "финансы": "ok", …},
  "хеш_остального": "sha256:…",
  "_итог": {"проверка_состоялась": false, "не_проверено": 8}
}
```

`поля` — ровно те, по которым идёт дифф (список берётся из `diff_counterparty.py`, не
дублируется: модуль импортирует оттуда перечень). `хеш_остального` — SHA-256 канонического
JSON всего, что не попало в `поля`: ловит «изменилось что-то вне отслеживаемого». ФИО
руководителя остаётся (по нему идёт дифф и санкционная сверка), адреса и прочие персданные
в отпечаток не кладутся сверх перечисленного.

Совместимость: `diff_counterparty.py` читает и старые полные снимки, и новые отпечатки
(определение по ключу `версия_формата`). Старые снимки не мигрируются и не удаляются.
`fetch_counterparty.py --save` продолжает сохранять снимок — интеграцию с `snapshot.save()`
делает интегратор после слияния потоков (поток H не трогает `fetch_counterparty.py`).

### 3.2 `scripts/watchlist.py` — список наблюдения и расписание

- `--добавить <ИНН> [--профиль <id>] [--комментарий "…"]`, `--убрать <ИНН>`, `--список` —
  файл `~/.cache/inn-check-ru/watchlist.json`.
- `--прогон` — по каждому ИНН из списка: `collect(режим="всё")` → отпечаток → дифф с
  предыдущим → отчёт только по изменившимся. Выход: JSON и `--human` (карточки изменений).
- `--установить-расписание` — печатает готовую строку crontab и строку launchd plist (macOS)
  с путями текущей установки. **Ничего не устанавливает само**: правка пользовательского
  crontab — за пределами того, что инструмент делает без спроса. Печать + инструкция.
- Тихий режим `--только-изменения` (для крона): пустой stdout, когда ничего не изменилось.

## 4. Перечень Росфинмониторинга — починка (поток I)

**Находка 19.09.2026:** XML-URL `terrorists-list-portal-simple` отдаёт 404, но полный
перечень доступен как HTML на `https://www.fedsfm.ru/documents/terrorists-catalog-portal-act`
(4,2 МБ, HTTP 200 с корнем УЦ Минцифры). Структура: четыре раздела в заголовках —
«Национальная часть» → «Организации» / «Физические лица», «Международная часть» → те же два.
Записи — элементы `<li>`, всего 23 821, из них 557 с ИНН.

Форматы записей:
```
6. АВТОНОМНАЯ НЕКОММЕРЧЕСКАЯ ОРГАНИЗАЦИЯ … , , ИНН: 1653019714, ОГРН: 1021603062150;
272. МЕСТНАЯ РЕЛИГИОЗНАЯ ОРГАНИЗАЦИЯ … , ИНН: 7901006096, ОГРН: 1027900000820, 17.05.1999;
740. ОБЪЕДИНЕНИЕ, ВКЛЮЧАЮЩЕЕ: КИСЛОГО ВИКТОРА ВЛАДИМИРОВИЧА, РОДИВШЕГОСЯ 03.08.1976 В …
```
Физлица идут как «ФАМИЛИЯ ИМЯ ОТЧЕСТВО, ДД.ММ.ГГГГ г.р., …» — разобрать на ФИО и дату
рождения; алиасы в скобках сохранять как отдельный список.

Задача: парсер HTML в `sanctions_check.py` (stdlib, `html.parser` или регулярки по `<li>`),
кэш как есть, сверка по ИНН — точная, по имени — точное совпадение с обязательной пометкой
«требует ручной сверки по дате рождения» (правило уже в KNOWN_LIMITS, не ослаблять).
Раздел записи («национальная/международная», «организация/физлицо») попадает в результат
сверки — это разный юридический вес.

Фикстура: вырезка из живого HTML (≤200 КБ, по нескольку записей каждого типа из каждого
раздела) + `eval/run_sanctions_eval.py` (сейчас санкции офлайн-eval'ом не покрыты вообще).
