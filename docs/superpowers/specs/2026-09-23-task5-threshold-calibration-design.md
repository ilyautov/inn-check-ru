## 1. Дизайн исследования

**Когорта.** Юрлица, опубликовавшие в ГИР БО отчётность за 2021 год, 30 000 компаний.
Выборка — по случайному числовому id организации ГИР БО из [1, 14 млн]
(детерминированная последовательность по seed, без повторов): id с периодом 2021 в
`/bfo/` входит в когорту. Это равномерная выборка по всем организациям, без страт и весов.

Первый вариант — страты поиска — отвергнут живым прогоном: дробление выдачи по префиксу
ОКВЭД покрыло 46% из 2,33 млн (у половины компаний код ровно равен префиксу, его не
отделить), фильтр `address` — полнотекстовый («МОСКОВСКАЯ» находит улицу Московскую в
Твери), части пересекаются.

**Признаки.** Ровно тот код, который видит пользователь: сырые ответы ГИР БО
(`bfo/` + `details`), оставлены только периоды ≤ 2021 → `fetch_counterparty.parse_finance`
→ `fin_scoring.score`. Дополнительно — непрерывные значения показателей (автономия,
ликвидность, падение выручки, ЧА, прибыль) для перебора порогов.

**Исход.** ЕФРСБ по ИНН через РФ-прокси.
- **банкрот** — есть дело о банкротстве, год заявления из номера дела (`А65-37758/2017`
  → 2017) ∈ {2022, 2023, 2024} — три года после отчёта. Сначала окно было 2022–2023, но
  предварительная частота 0,34% давала ~50 случаев на 15 000; окно расширено, когорта
  удвоена (решение пользователя 23.09.2026);
- **исключён** — год заявления ≤ 2021: на дату отчёта компания уже была в суде, её
  отчётность — не прогноз, а симптом (утечка из будущего наоборот);
- **выжил** — дела нет (или год заявления ≥ 2025 — вне окна, считается «не банкрот
  в окне»).
- «Производство прекращено» (`ProceedingsStopped`) бывает и без введённой процедуры —
  считается случаем, а в отчёте есть расчёт без таких случаев (чувствительность).
Добровольная ликвидация и исключение из ЕГРЮЛ — не банкротство и в метриках считаются
«выжил» (для контрагента это тоже плохо, но калибруется банкротство).

**Двухфазная выборка.** Фаза 1 — вся когорта размечается по ЕФРСБ (дёшево, 1 запрос).
Фаза 2 — детальные формы 2020–2021 для всех случаев и случайных 3000 выживших; выживший
весит 1/f, где f — доля отобранных. На весах PPV и лифт относятся к генеральной
совокупности, а не к обогащённой выборке; бутстреп — раздельно по случаям и контролям.

**Метрики.** На каждый флаг `fin_scoring` при действующем пороге: доля флагнутых,
точность (PPV), полнота, лифт = PPV / базовая частота, 95% ДИ бутстрепом (2000 повторов,
фиксированный seed). Перебор порога по сетке — кривая полноты/лифта; порог не
«оптимизируется до знака»: канон меняется, только если новый порог лучше по лифту
при сопоставимой полноте и ДИ не перекрываются. Отдельно — срез «выручка 2021 ≥ 10 млн»
(операционные компании, для которых инструмент и работает).

## 2. Код

`calibration/` — инструмент сопровождающего, **в пакет не входит** (py-modules
перечислены явно). Только stdlib.
- `socks5.py` — SOCKS5 (RFC 1928 + логин/пароль RFC 1929) поверх `socket`, HTTPS через
  `ssl.wrap_socket` поверх туннеля; `urllib`-хендлер. Движок SOCKS5 по-прежнему не
  принимает — это решение не меняется.
- `collect.py` — стадии `когорта` → `ефрсб` (может идти `--следом`) → `гирбо`; кэш
  сырых ответов в `~/.cache/inn-check-ru/calibration/`, повторный запуск продолжает с
  места обрыва; общий темп на хост: ГИР БО 3 запроса/с, ЕФРСБ 1,5/с (потоки только
  перекрывают задержку); при ответе ЕФРСБ, отличном от 200/JSON, стадия останавливается
  (никаких повторов «пробить»); сетевой обрыв — до 10 попыток за ~25 минут.
- `evaluate.py` — сборка набора, метрики, `calibration/report.json` +
  `calibration/cohort_2021.csv` (ИНН, признаки, исход — всё из открытых реестров).
- `eval/run_calibration_eval.py` — синтетические фикстуры: разбор года из номера дела,
  исключение «уже в суде», отсечение периодов > 2021, метрики на известной матрице;
  мутации должны кусаться.

Прокси — только из `INN_CHECK_CALIBRATION_PROXY`; в репозиторий, отчёт и логи
логин/пароль не попадают (маска как в `proxy.маска`).

## 3. Что публикуется

`references/kalibrovka.md` — методика, выводы и таблицы «флаг → порог → доля → полнота
→ точность → лифт → ДИ → покрытие», размер выборки и базовая частота, ограничения. Таблицы
генерирует `evaluate.py --справочник` из `report.json`, eval сверяет их с отчётом.
Порогов `fin_scoring` в `data/canon_ru.json` нет (они в `scripts/fin_scoring.py`), поэтому
ссылка на калибровку — комментарием у констант, строкой в SKILL.md и в KNOWN_LIMITS.

**Итог прогона 24.09.2026:** пороги не меняются — ни один порог сетки не лучше
действующего по лифту при сопоставимой полноте с непересекающимися ДИ.

Две находки прогона, которых в дизайне не было:
- `/bfo/` отдаёт только пять последних периодов (в 2026 — 2021–2025), формы за 2020 нет.
  Прошлый год собирается из колонок `previous*` формы 2021 (`evaluate.только_до`).
- Флаг движка без исходного показателя (у ~2/3 компаний нет строк 1200/1500) — вне
  расчёта, а не «не флагнут»; иначе покрытие ликвидности было бы 100% вместо 32%.

## 4. Ограничения (пишутся в отчёт)

- Одна когорта (2021) и одно окно (2022–2024): период санкционного шока; перенос на
  другие годы не проверен.
- Когорта — организации с опубликованной в ГИР БО отчётностью; кто не сдал отчётность
  за 2021, в выборку не попадает (а среди будущих банкротов таких, вероятно, больше).
- ЕФРСБ отдаёт последнее дело; более раннее дело той же компании не видно.
- Транзитный профиль и чеклист однодневки не калибруются: исторических численности и
  массовости адреса в открытых данных нет.
- Банкротство — не единственный плохой исход для контрагента (исчезновение, ФССП);
  калибруется только он.
