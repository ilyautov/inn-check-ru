# Контракт полевых доказательств, версия 1

Читать перед интерпретацией решающих claims, raw-ссылок, полноты поиска и допустимости рекомендации.

Состояние: `enrich`/`validate_evidence` подключены к действующим скореру,
резолверу, сборщику, снимку и модели Markdown/DOCX. `evaluate` материализует один
расчёт существующего движка. Это офлайн-контракт происхождения и полноты,
а не подтверждение точности реестров или нормативной применимости непроверенной формы.

## Публичный интерфейс

```python
def enrich(fetch: dict, *, now: str, raw_refs: dict | None = None) -> dict: ...
def evaluate(fetch: dict, *, profile: str, now: str) -> dict: ...
def validate_evidence(fetch: dict) -> list[dict]: ...
```

`enrich` возвращает глубокую копию исходного fetch. К существующим ключам
добавляется `_evidence = {schema_version, claims, conflicts, applicability,
rules_version}`. Схема `Claim` и `RawRef` зафиксирована TypedDict в модуле;
дополнительных полей в Claim нет. Нет сетевых вызовов, записи файлов или
повторного финансового расчёта. ИНН проверяется существующим публичным
`fetch_counterparty.validate_inn`; метаданные формы не могут заменить тип
субъекта, определённый по принятому ИНН. Валидный 12-значный ИНН в существующем
контракте коллектора относится к ИП.

`now` обязателен, ISO 8601 с часовым поясом, нормализуется в UTC. Недопустимый
ввод и повреждённые явно предоставленные ссылки вызывают `ValueError(code)`.
Неизвестная версия существующего sidecar отвергается с `unsupported_schema`.
Старый fetch без sidecar читается как `legacy_untraced`.

## Материализованное решение и старые расчёты

`evaluate` сохраняет нормализованные состояния источников в
`_evidence.source_states`. Рендер сохранённого решения использует именно эти
состояния: текущие часы и новые правила доступности не переоценивают старое
досье. Явный `materialized=True` без сохранённых состояний возвращает
`materialized_source_states_required`; обычный путь построения досье остаётся
совместимым. Структурный максимум 32 зависимостей фиксирован для schema 1,
а не берётся из изменяемой бизнес-политики при чтении старого результата.

Финансовый скорер добавляет `_input_identity`: привязку к фактическим входам,
субъекту, годам, выбранной численности/источнику и версии кода/правил.
Резолвер не выдаёт подтверждённый финансовый вывод из отдельно переданного
старого или непривязанного `fin`: причина `financial_input_mismatch` остаётся
unknown. Чтобы получить новый вывод, вызывающий явно считает текущие входы
тем же `fin_scoring.score`. Эта привязка защищает от случайного смешения
расчётов; она не является подписью достоверности присланных пользователем данных.

## Что является фактом

`knowledge`: `known`, `unknown`, `not_applicable`, `conflict`. Ноль численности
сохраняется как наблюдаемое число; `None` — отсутствующее необходимое поле.
Булева численность, отрицательная численность и нечисловая строка не становятся
известной численностью. Входной fetch при этом сохраняет исходные байты JSON
на уровне своих значений.

`False`, пустой список/словарь и строковое отрицание требуют явных
`search_scope.subject_inn`, `search_scope.query` и `coverage_complete=true`.
Ноль количества производств ФССП или проверок ЕРКНМ также является отрицанием,
а не автоматически завершённым поиском. Недоступный источник, пустой
транспортный ответ и неполная пагинация не подтверждают отсутствие риска.

Без raw известное наблюдаемое значение сохраняется, но получает
`reason_code=raw_unavailable`; `raw_ref` содержит null вместо придуманного хеша
или пути. Если записанные ответы есть, но поле не сопоставлено, availability
равна `unmapped_locator`. Это ограничение проверяемости, не доказательство
ложности значения и не утверждение достоверности источника.

## Явный адаптер записанных ответов

`raw_refs` не является манифестом пакета. Сборщик/импортёр передаёт уже прочитанные
байты записанного ответа и явную карту. Модуль не открывает произвольные пути из
данных и не угадывает JSON Pointer по имени нормализованного поля.

```python
import hashlib

body = saved_response_bytes  # реальные байты из пакета, не json.dumps(fetch)
raw_refs = {
    "responses": {
        "r1": {
            "source_id": "дампы_фнс",
            "subject_inn": "7707083893",
            "request": {"subject_inn": "7707083893"},
            "body": body,
            "sha256": hashlib.sha256(body).hexdigest(),
            "retrieved_at": "2026-10-16T09:00:00Z",
        }
    },
    "fields": {
        "дампы_фнс.численность_сотрудников": [{
            "response_id": "r1",
            "locator": "/records/0/staff",
            "subject_locator": "/records/0/inn",
            "transformation": "integer_v1",
        }]
    },
}
```

Пример карты применим **только если именно такие пути есть в конкретных байтах**.
Проверяются SHA-256 тела, источник, субъект запроса, субъект ответа и ИНН
выбранной записи, разрешение обоих указателей, преобразование и совпадение с
нормализованным значением. Несовпадения не превращаются в доступную ссылку:
`raw_hash_mismatch`, `foreign_subject`, `source_mismatch`, `unmapped_locator`,
`transformation_mismatch`. Неизвестная карта поля отвергается с
`unsupported_field_mapping`.

Поддерживаются `identity_v1`, `integer_v1`, `number_v1`; булевы числа и NaN/Infinity
не принимаются числовым преобразованием. Для альтернативного ответа того же
поля карта содержит `candidate=true`: сохраняется **проверенное значение этого
ответа**, которое может отличаться от выбранного legacy значения. Несколько
карт задаются списком. `source_id` в карте явно выбирает второго поставщика;
его ID должен совпасть с ID захваченного ответа. Это не второй скорер.

Значение Claim с доступным raw точно воспроизводится указанным преобразованием
указателя, включая тип JSON. После проверки raw скрытого преобразования нет.
Например, строка `"3"` при `identity_v1` остаётся строкой и для численности
получает `unknown:schema_invalid`; явное `integer_v1` даёт известное число 3.
Денежные строки с форматированием требуют `number_v1`/`integer_v1`. Булевы,
строковые и составные значения финансовых листов при `identity_v1` остаются
наблюдаемыми, но не считаются известной суммой или раскрытым листом упрощённой
формы, даже с `candidate=true`. Без raw допустимое legacy преобразование
численности/финансов также записывается в `transformation`.

Дополнительные элементы карты: `period`, `published_at`, `effective_at`,
`first_observed_at`, `date_locators`, `search_scope`, `coverage_complete`,
`upstream_dataset`, `relation`. Период — `{start, end}` с календарными датами;
адаптер отвечает за семантическое соответствие периода датасету/полю. Модуль
проверяет форму периода. Моменты публикации/состояния используются лишь при
`date_locators={"published_at": "/...", "effective_at": "/..."}` и совпадении с
датой, разрешённой в записанном теле. Произвольная подпись даты без такого
указателя не входит в known-at. `first_observed_at` допускается также из
метаданных захвата ответа; время загрузки не подменяет публикацию.
Указатель даты ограничен той же проверенной записью субъекта, что и значение;
дата соседней компании не может обновить старое отрицание. Вложенные чужие
ИНН отвергаются и при совпадающем ИНН заголовка. Автоматического исключения для
дат ревизии всего ответа нет: адаптер не должен выдавать общую метадату за
дату конкретной записи; отдельная схема такой ревизии здесь не реализована.

`validate_evidence` возвращает список `{code, claim_id}`. Оно проверяет схему,
субъекта, формат SHA, ID, ссылки, лимит 32 зависимости и циклы. Без переданных
исходных байтов повторная проверка криптографического соответствия raw
невозможна: для неё повторно вызывается `enrich(..., raw_refs=...)` либо
проверяется исходный evidence pack. Структурная проверка sidecar не доказывает
подлинность ответа сервера.

## Время и происхождение

Политика `data/evidence_policy.json` версионирована и содержит основание каждого
срока. Для санкций применяется 7 суток из существующего
`sanctions_check.CACHE_TTL_DAYS`; на точной границе `now >= valid_until` факт
становится `unknown:stale`. Без подтверждённой даты состояния срок не
придумывается (`unknown:revision_unknown`). Для ежегодной отчётности и ССЧ
период сохраняется; произвольный общий TTL не назначен. Для реестров TTL
доступности сети 24 часа не используется как срок истинности юридического
факта. Null `valid_until` не означает бессрочную текущую актуальность.

Период ССЧ берётся из фактического `риски.среднесписочная_за_год`, алиаса
`численность_год`, а для старого дампа — также `год`. Конфликтные/некорректные
алиасы не выбираются молча. Год строк бухгалтерской отчётности берётся из
карточки года. Запрос в следующем месяце не переименовывает период. При
повторном enrich ранее сохранённого sidecar первое наблюдение сохраняется;
время нового чтения меняется отдельно. Будущая дата не становится публикацией
или первым наблюдением раньше времени; исходные метаданные не удаляются из
legacy fetch или записанного ответа.

Известное историческое положительное событие с проверенным raw и датой
состояния сохраняется при недоступности текущего источника. Это не закрывает
текущее покрытие источника. Разные периоды не конфликтуют. Разные значения одного
поля одного периода сохраняются все; `conflicts` содержит отсортированные
`candidate_claim_ids`, `selected_claim_id=null` и причину. Порядок поставщиков
не влияет на результат. Автоматического выбора победителя нет.
Числа 100 и 100.0 эквивалентны при проверке raw и поиске конфликтов, в том
числе внутри составного значения; булевы True/False отличаются от 1/0.
Точные дубли одного Claim ID сворачиваются. Если карты одного ID расходятся
по покрытию, области поиска, датам, происхождению или другим метаданным,
весь ввод отвергается с `inconsistent_duplicate_claim` независимо от порядка
карт и текущей свежести. Последняя карта не может повысить полноту поиска.

`origin_family` описывает происхождение, а не порядок запуска зависимых
источников. Зеркала ЕГРЮЛ не являются независимыми подтверждениями. Неизвестное
семейство остаётся null. `manual_observation` не наследует государственное
семейство; доверие госисточнику ему не присваивается.

## Покрытие листов и применимость

Каждый путь из `profiles_ru.json` присутствует в policy и в claims, в том числе
при отсутствии значения. Новый неизвестный путь профиля ломает гейт
`unsupported_profile_path`; он не выпадает из знаменателя молча.
`финансы.отчётность_по_годам.<год>.строки.<код>` покрывает все реальные входные
строки текущего скорера: 2110, 2400, 1600, 1300, 1500, 1400, 1200, 1250 и его
существующие именованные алиасы. Отсутствующий необходимый предыдущий год
сохраняется как missing; год не выводится из текущей даты.

`fin.*` здесь остаётся unknown: исходы правил появятся только из авторитетного
`fin_scoring.score` в 1C. `depends_on` уже связывает каждый финансовый путь с
листами и периодами; транзит включает обе выручки, численность и её год.
Выручка 2025 + ССЧ 2023 дают `period_mismatch`, не проверенный транзит. Правила
скоринга и пороги не продублированы.

`фссп.сумма` сохраняется как фактический legacy ввод. Он не раскладывается на
текущий/погашенный долг. Новые отдельные поля `фссп.долг_текущий` и
`фссп.долг_погашенный` имеют рублёвую единицу и пока unknown, если нет отдельных
входов и временного основания. Нулевой погашенный долг не придумывается.

| Сегмент | Применимость финансовых правил | Ограничение |
|---|---|---|
| Полная форма | `applicable` после проверенной raw-ссылки на форму | Недостающие листы остаются unknown, входят в необходимые проверки |
| Упрощённая | Конкретное правило `applicable`, если необходимые финансовые листы раскрыты; иначе `unknown` | Слово simplified не исключает ЧА/ликвидность; красный лист не скрывается формой |
| ИП | `not_applicable:not_measurable_for_form` для финансовых правил корпоративного баланса | Тип должен следовать принятому ИНН; произвольная подпись IP не меняет юрлицо |
| Банк | `unknown:unsupported_form` | Банковские коэффициенты и пороги не придуманы |
| НКО | `unknown:unsupported_form` | Специальная модель не реализована |
| Ограниченный доступ | `unknown:not_disclosed` | Отсутствие публикации не означает отсутствие деятельности или риска |

`applicability` содержит `subject_type`, `reporting_form`, `form_version`,
`form_evidence_ids`, `source_coverage`, `rules`. Проверенная ссылка на форму —
Claim поля `финансы.форма_отчётности` с доступным raw. `_reporting` задаёт
контекст, но один этот блок не делает форму проверенной. ОКВЭД не используется
для угадывания формы. `unknown` в rules нельзя исключать из знаменателя как
`not_applicable`; итоговый знаменатель и рекомендация принадлежат задаче 1C.

**Эмпирическая проверка всех шести сегментов на реальных, отдельно проверенных
паспортах/образцах форм здесь не проведена.** Если перед сохранением применена редакция секретов, SHA относится к этим
сохранённым байтам; они не называются неизменённым оригиналом ответа источника.
Синтетические тесты подтверждают
поведение контракта; они не подтверждают нормативную полноту форм, истинность
реестров или юридическую достаточность проверки. Связь с raw доказывает
согласованность входа и преобразования, не подлинность публикации.

## Проверка

```sh
python3 eval/run_evidence_contract_eval.py
python3 eval/run_evidence_pack_eval.py
python3 eval/run_fin_eval.py
python3 eval/run_profiles_eval.py
```

Фокусированный набор проверяет missingness, неизменность входа, реальные байты
локального пакета, повреждённый SHA/субъект/указатель, все пути профилей,
зависимости/циклы, перестановку поставщиков, периоды, UTC, границу срока,
исторический positive при потере текущего покрытия и все шесть сегментов форм.


## Авторитетное решение, совместимость и документ

`evaluate` возвращает ровно `{fetch, fin, assessment, metadata}`. `metadata`:
`schema_version=1`, действительная версия пакета, `rules_version` (SHA-256
canonical JSON текущих canon/profiles/evidence policy), UTC `evaluated_at`,
`decision`. Один вызов существующего `fin_scoring.score`; исходные
`оценки_сигналов`/`версия_оценок=1` остаются авторитетными. Новый слой связывает
их с листами, периодами и применимостью и не считает параллельные признаки.
`fetch._decision == assessment._decision == metadata.decision`.

Старые `score` и `resolve` проходят тот же строгий адаптер. Формы JSON/API
сохранены; прежнее небезопасное отрицание без scope не сохраняется ради зелёного
светофора. Сырой математический финансовый флаг может сохраниться при
непроверенной форме, но профиль оставляет соответствующее утверждение unknown.
Метка ИП берётся из принятого ИНН, а не произвольного поля `тип`.

Coverage считает применимые обязательные правила профиля, в том числе красный
severity override. Неприменимое правило исключается; unknown остаётся в
знаменателе. `can_recommend=false` при любом необходимом пробеле, конфликте,
устаревании или неподдержанной форме. `нейтрально` всегда `facts_only` и
`can_recommend=false`. Красный наблюдаемый сигнал остаётся видимым и при
неполной проверке, однако безусловная рекомендация по сделке не выдаётся.

`enrich` при повторной оценке сохраняет проверенные raw IDs/указатели, даты и
кандидатов неизменившихся полей. Старое наблюдение не получает новую дату
публикации. Старые непроверяемые значения могут обновить retrieved_at как
адаптацию; TTL и будущее наблюдение учитываются отдельно. Финансовый derived
Claim ссылается на настоящие листья, включая выбранный источник численности и
все переданные поля её года. Source/year Phase 0 не заменяются датой запроса.

`оценки_сигналов.*.достаточные_зависимости` дополняет прежние `зависимости`:
авторитетный скорер записывает поддержку фактически выбранной ветки, не меняя
математику и пороги. Для транзита рост не выше порога сам доказывает отсутствие
сочетания «высокий рост и малая численность»: достаточно двух известных выручек.
При высоком росте необходимы выбранная численность и сопоставимый год. Все
переданные алиасы года проверяются; отсутствующее альтернативное имя поля не
становится отдельным обязательным фактом. Неизвестный обязательный лист,
неподдержанная карта поля или несопоставимый необходимый период оставляют
derived Claim неизвестным. `depends_on` означает AND всех фактически необходимых
листьев; известный derived Claim не может ссылаться на неизвестный лист.
Недоступность источника продолжает влиять на остальные обязательные проверки
и общую рекомендацию, даже если отрицательный транзит уже доказан выручками.

Legacy-импортёр вправе передать явные сведения о полноте в
`_evidence_scope[field] = {search_scope, coverage_complete}`. Это объявление
импортёра с `relation=legacy_untraced` и `raw_unavailable`; оно не становится
государственным raw-подтверждением. Семантическая дата без checked locator
по-прежнему не доказывает публикацию или актуальность санкционного перечня.

Snapshot сохраняет `_evidence`/`_decision` и фактические решающие листья для
последующего восстановления; метаданные не меняют бизнес-хеш «остального» из-за
одного нового retrieval. Старые снимки читаются без придуманных ссылок.
Досье выводит ID решающих утверждений, raw availability/response/hash/pointer,
периоды, scope, зависимости, конфликты и пробелы. Рекомендация привязана к
известным claim IDs; неизвестные не подставляются как отсутствие.

`dossier.собрать(..., materialized=True)` предназначен для сохранённой ревизии:
структурная валидация, исходные fin/assessment/decision и метаданные без
переоценки текущими правилами или часами. Несовместимая schema отвергается.
Обычный вызов без флага сохраняет API и адаптирует вход по текущим правилам.
Наличие исторического периода отчётности или roundtrip снимка само по себе
не доказывает публикацию до даты сделки; полный replay/cutoff — отдельный этап.

## Реальный захват и callback API

```python
with fetch_counterparty.capture_session(inn, secrets=(), on_response=None) as cap:
    fetch = fetch_counterparty.collect(inn, on_source=None)
refs = cap.raw_refs(fetch)
# cap.responses: существующая форма evidence_pack + response_id,
# subject_inn, sha256, capture_format, original_response_preserved.
```

Каждый ответ получает собственный response_id. Сессия и бюджет времени
изолированы через contextvars и передаются четырём collector workers.
`on_response(record)` получает безопасную независимую копию сразу после
санитизации; `on_source(sid, data, availability)` получает копии готовых
результатов в порядке завершения futures. Ошибка durable callback прерывает
операцию; она не маскируется недоступностью реестра. API не пишет файлы сам.

Карта raw строится только из фактических записанных JSON-байтов и проверенных
путей существующих EGRUL/PB полей (статус/даты с INN выбранной записи).
Агрегат финансового detail без ИНН-контекста, HTML и неподдержанный парсер
остаются `unmapped_locator`/`raw_unavailable`. Совпадение значения с произвольным
соседним JSON-полем не используется как происхождение. Нет вымышленных
`/normalized` указателей и нет обещания покрытия всех реестров захватом.

Новые записи используют canonical `redaction.redact`. Ключи Checko/DaData и
пароль настроенного proxy известны до первого запроса; дополнительные
header-only credentials передаются через `secrets`. Помеченные token/_token_pb,
Authorization и EGRUL `t` обнаруживаются в текущем ответе до callback; повторные
копии и последующий URL с токеном редактируются. Произвольную немаркированную
строку нельзя распознать как неизвестный секрет: её нужно явно передать в
`secrets` до записи. Полное окружение не сохраняется и не считается списком
секретов.

`capture_format=sanitized_json_v1` означает санитизированные JSON-байты;
`withheld_non_json_v1` — непрозрачное тело исключено (сохранены метаданные и
пустые байты). Это ограничение безопасного захвата, а не оригинал ответа.
`original_response_preserved` честно сравнивает сохранённые bytes с полученными;
SHA-256 принадлежит именно сохранённым bytes. Callback-байты, IDs и хеши
не меняются задним числом. Если новый явно переданный secret потребовал бы
изменения уже помеченной записи, новый пакет отказывается с
`captured_bytes_redaction_mismatch`, вместо подмены bytes под старым hash.
Проверка существующих пакетов и immutable ручные версии не переписываются.
