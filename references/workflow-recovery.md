# Резервная копия и восстановление workflow

Читать перед переносом runs, восстановлением после сбоя, сменой версии пакета или удалением данных. Работайте с локальной кооперативной файловой системой: блокировки сетевых FS, недоверенный процесс того же пользователя и произвольное редактирование файлов за пределами API не входят в гарантии.

## Что сохранять

Остановите всех писателей: CLI-сбор/refresh/manual/export, MCP-сервер, native host и OS-задачи мониторинга. Убедитесь, что принадлежащие им процессы завершились. Затем скопируйте **весь каталог `<runs>/<run_id>/`** в резервную копию: HEAD, revisions, raw, capture journal, artifacts и их registry, включая оставшиеся orphan-файлы. Не собирайте копию только из последнего JSON или DOCX. Для полного мониторинга отдельно сохраните workspace с watchlist, runs, events, журналом и подтверждениями доставки; policy/ключи храните отдельно как конфигурацию хоста.

Оператор выбирает приватный новый локальный root без symlink/reparse points и копирует каталог run туда, не смешивая с существующим run того же ID. Права должны сохранять доступ владельца. Не переносите активную блокировку на работающий процесс.

## Проверить копию

Используйте установленное совместимое колесо из временного venv, а не одно успешное HTTP-ответное сообщение или один `show`. Следующий код выполняется Python того же venv. Значения путей/ID замените собственными; это read-only проверка, не инструкция редактировать хранилище:

```python
import hashlib
import run_store

root = "/absolute/private/restored/runs"
run_id = "YOUR-SAVED-UUID4"
head = run_store.read(run_id, root=root)  # проверяет всю committed hash chain
for revision in range(1, head["revision"] + 1):
    record = run_store.read(run_id, revision=revision, root=root)
    refs = record["payload"]["metadata"].get("raw_refs", {})
    for item in refs.get("responses", {}).values():
        body = run_store.read_raw(run_id, item["sha256"], root=root)
        assert hashlib.sha256(body).hexdigest() == item["sha256"]
# Проверяет также записанные raw captures, ещё не вошедшие в payload.
run_store.captured_responses(run_id, root=root)
for artifact in run_store.list_artifacts(run_id, root=root):
    body = run_store.read_artifact(run_id, artifact["artifact_id"], root=root)
    assert hashlib.sha256(body).hexdigest() == artifact["sha256"]
print("committed revisions, referenced raw and registered artifacts verified")
```

Сравните реестр файлов и SHA-256 исходной остановленной копии с восстановленным каталогом, включая orphan-файлы. Их сохранение нужно для расследования; не выбирайте их как committed revision и не переназначайте HEAD. `read` выбирает только цепочку, достижимую от committed HEAD, `read_artifact` — только запись в registry. Совпадение хешей подтверждает целостность скопированных байтов, не истинность данных источника.

Затем проверьте восстановленный `original` replay с cutoff не раньше нужной ревизии и при заблокированном сетевом транспорте. Он не должен обращаться к источникам, применять новые правила или менять файлы:

```sh
inn-check-workflow run show "$RUN_ID" --store /absolute/private/restored/runs --json
inn-check-workflow run replay "$RUN_ID" --mode original --cutoff 2026-10-16T23:59:59Z --store /absolute/private/restored/runs --json
```

Здесь дата — пример; возьмите момент, включающий вашу ревизию. Сравните возвращённые payload/manifest и хеши всех файлов до/после. `current_rules` — отдельный явный перерасчёт, он не заменяет проверку исходного решения. [Контракт replay](historical-replay.md).

## Атомарность и сбои

Запись ревизии использует OS-lock, CAS по `expected_revision` и атомарное переключение HEAD. Потерянный ответ не означает потерянную запись: сначала прочитайте run/найдите operation_id; повторяйте то же намерение с тем же UUID и данными. При `revision_conflict` перечитайте и подтвердите новую привязку. При `operation_conflict` нельзя менять данные старого UUID.

При disk-full/ошибке доступа (`storage_error`), `lock_timeout`, `unsafe_path`, `corrupt_store` или `unsupported_schema` остановите новые записи, сохраните копию и причину. Не объявляйте запись успешной без committed read. Устраните свободное место/права/живого владельца блокировки, затем повторите контролируемо. Lock-файл сам по себе не означает зависший процесс: блокировка принадлежит ОС. Не удаляйте файл под активным писателем; после завершения процессов OS-lock освобождается. API не чинит повреждённую цепочку и не выбирает самый большой номер файла автоматически.

TTL факта означает свежесть для решения; он **не удаляет** raw-байты. Автоподчистки raw и orphan-файлов нет. Ручное удаление может уничтожить проверяемость старой ревизии. Внутри raw/отчётов могут быть публичные персональные сведения: выберите срок хранения и доступ самостоятельно; не называйте архив обезличенным.

## Откат пакета и схемы

Перед откатом остановите писателей и сделайте копию. Откат Python-пакета выполняйте в отдельном venv; каталог данных не мигрируйте и не перезаписывайте. `unsupported_schema` означает, что читатель видит схему, которую не понимает: нужен совместимый читатель, а не изменение `schema_version` вручную.

Локальная [installed-проверка](../eval/run_installed_workflow_eval.py) Python 3.12 восстановила все **7 committed ревизий**, связанные raw и зарегистрированные артефакты, выполнила original replay без сети и сравнила хеши. Фактический откат на колесо 1.12.3, собранное из BASE `3e06046`, сохранил store; старый одноразовый CLI работал, а новый entrypoint workflow отсутствовал. У 1.12.3 ещё не было workflow: отсутствие команды — `unsupported client`, **не** полученный от старого релиза `unsupported_schema`. Отказ текущего читателя на искусственной будущей схеме 999 и моделирование schema-older reader проверены отдельно без изменения данных. Это синтетический локальный drill, не проверка на пользовательском хосте и не обещание совместимости с любым будущим релизом.

Ни одна из этих процедур не публикует релиз, не регистрирует расписание и не отправляет файлы. [Установка и маршрут](agent-workflow.md), [матрица](capability-matrix.md).
